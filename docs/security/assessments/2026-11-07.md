# Dynamic scan (DAST) — 2026-11-07

**Commit scanned:** `fae657bd`, built into the production image and run as a
throwaway stack. **Fix from this pass:** R455 (a `Permissions-Policy` header),
commit recorded below.

## What this is, and what it is not

This is the scanner-led test of the **running application** that the
[2026-11-06 schema audit](2026-11-06-schema.md) said was planned and had not
happened. It ran OWASP ZAP and Nuclei against a throwaway copy and looked at
the HTTP surface the schema audit could not: response headers, framing, CORS,
information disclosure, and the ~10,500 generic web/CVE checks Nuclei carries.

It is **not** a full penetration test, and SECURITY.md's statement that there
is no penetration-test report stays true. Specifically:

- **Unauthenticated surface only.** ZAP and Nuclei were given no credentials,
  no API key and no embed key. They exercised what an anonymous caller reaches.
  The authenticated authorization surface — who may read or write whose rows
  once signed in — is covered by the code-and-schema reviews R420–R454, not by
  this scan.
- **ZAP and Nuclei, not sqlmap or ffuf.** The schema audit named four tools for
  this round. Two ran. sqlmap (SQL-injection) and ffuf (content discovery) did
  not; the app's data paths are parameterised and reviewed (R424–R426, the
  read-only guard), and ZAP's spider covered discovery for this pass, but a
  dedicated injection and fuzzing pass is still owed and folds into the AWS
  staging test below.
- **A lean target under a 10 GB cap.** The Docker VM on the test host is capped
  at 10 GB, so the throwaway ran the application container, Valkey and a full
  Supabase, but not the Spark / lakehouse / Qdrant / notebook / docgen service
  suite. Routes that hand work to those services return their unavailable state
  rather than their live behaviour; nothing behind them was scanned.
- **Plain HTTP, locally.** The throwaway has no TLS. Findings that reduce to
  "no HTTPS" are a property of the test rig, not the application, which emits
  HSTS over HTTPS and is meant to sit behind a TLS-terminating load balancer.

## Method

1. **Build an isolated throwaway.** The production image was rebuilt with
   throwaway Supabase keys so its browser bundle can only reach the throwaway
   project, and the served bundle was checked to contain **zero** references to
   the real hosted project before any scanner was pointed at it. The stack ran
   as compose project `pentesttarget` on `http://host.docker.internal:8080`.
2. **Scope every scanner to that origin.** ZAP's context and Nuclei's target
   were `host.docker.internal:8080` and nothing else. No scan touched the real
   hosted Supabase project or any third party.
3. **Keep it safe.** No out-of-band interaction (`-no-interactsh`, no OAST
   rules); no denial-of-service, fuzzing or intrusive templates
   (`-exclude-tags dos,fuzz,intrusive`); rate-limited to 40 req/s.
4. **Triage every match against the source.** Each ZAP alert and Nuclei match
   below was read against the code that produces it, and marked false positive,
   by design, environmental, or a real gap.

## Findings

No scan found an exploitable vulnerability in the application. Every alert was
one of: a false positive on example/teaching content, a documented design
choice, a property of the local test rig, or low-severity defence-in-depth. The
one change made (R455) adds a header the app lacked.

## Remediation — R455

A `Permissions-Policy` header was added to `serverSecurityHeaders.mjs`,
denying the powerful browser features the application never uses
(`accelerometer`, `camera`, `display-capture`, `geolocation`, `gyroscope`,
`magnetometer`, `microphone`, `payment`, `usb`). Verified against the source:
no `getUserMedia`, geolocation, `PaymentRequest`, WebUSB or motion-sensor API
appears anywhere in `src`, so this is pure defence-in-depth with no effect on
behaviour. It is env-configurable (`PERMISSIONS_POLICY`; empty sends none) and
is covered by `tests/unit/securityHeaders.test.ts`, which exercises the real
middleware and srvx path. No `default-src`/`connect-src` change was made
blindly, because the module's own report-only trial is the safe way to tighten
those per deployment.

**Commit:** recorded in `ADVERSARIAL_LOG.md` under R455.

## Recommendations for the AWS deployment

These are deployment-configuration items, not application bugs. They matter
because the throwaway exposed what co-location looks like:

1. **Set `VALKEY_PASSWORD` and keep Valkey off public networks.** The isolation
   and AUTH story is already in place (loopback bind in compose, installer-
   generated password, VA-41 warning); the one standing action is to *use* it —
   a generated password and a private-network path for the multi-instance
   options (C/D), plus confirming the pinned Valkey `8.1.11` image carries the
   backported Lua fixes for CVE-2025-46817/46818/46819/49844 (bump if not).
2. **Terminate TLS at the load balancer and keep HSTS on.** The app already
   emits HSTS over HTTPS; set `HSTS_MAX_AGE`/`HSTS_INCLUDE_SUBDOMAINS` for the
   production lifetime.
3. **Tighten the CSP for the known deployment.** Run the built-in
   `CONTENT_SECURITY_POLICY_REPORT_ONLY` trial in staging to learn the exact
   `connect-src`/`img-src`/`style-src` the deployment needs, then enforce a
   `default-src`-anchored policy via `CONTENT_SECURITY_POLICY`.

## Has a running install been affected?

No. The scan ran only against a throwaway copy on `:8080`; the real hosted
project was never a target. The one code change (R455) adds a response header
and changes no behaviour.
