# Schema audit — 2026-11-06

**Commit audited:** `3924c374`, with all 288 migrations applied to an empty self-hosted
Supabase stack holding no real data. **Fixes:** R454, migration `20261110000000`.

## What this is, and what it is not

This reads Postgres's own catalog: what the sum of every migration, and Supabase's
default grants, actually left behind. The 2026-10-25 assessment reviewed access by
reading the code and the migrations, and this looks at the result instead.

**This is not a penetration test, and nothing here should be read as one.** A
scanner-led test of the running application was planned for this round, using OWASP ZAP,
Nuclei, sqlmap and ffuf against a throwaway copy. It did not happen: no scanner ran, and
no traffic reached the application. So the HTTP surface (75 API routes, 474 server
functions), and with it headers, SSRF, XSS and request handling, was **not** tested
here. SECURITY.md's statement that there is no penetration-test report remains true.

## Method

1. Run [`scripts/schema-audit.sql`](../scripts/schema-audit.sql), which is read-only.
2. Read the body of every `SECURITY DEFINER` function a signed-out caller can run, and
   every function whose guard could be affected by NULL. A function that mentions
   `auth.uid()` has not been shown to check it.
3. For each suspicion, attack it as the real database role, with real rows, in a
   transaction that is rolled back. Every result below was measured that way.
4. Repeat each attack with the fix applied, alongside the things that must keep working.

### SA-2026-11-06-01: a guard that came out NULL did not refuse

`budget_spend_since` is `SECURITY DEFINER`, so it reads every user's traces, and it
guarded that with:

```sql
IF NOT (
  (_user_ids IS NULL AND auth.uid() = _user_id)
  OR public.is_superadmin(auth.uid())
  OR COALESCE(auth.jwt() ->> 'role', '') = 'service_role'
) THEN
  RAISE EXCEPTION 'not authorized';
```

With nobody signed in, `auth.uid()` is NULL, so `auth.uid() = _user_id` is NULL, not
false. `NULL OR false OR false` is NULL, `NOT NULL` is NULL, and `IF NULL` does not take
the branch. The exception was never raised.

Measured, as the `anon` role with no token, against a user with $1.23 of traces: the
function returned `1.23`. It needed the user's id, and anyone with the project's public
key could call it. Fixed by wrapping the condition in `COALESCE(..., false)`, and by
revoking `EXECUTE` from `anon`, so either alone would have stopped it.

**The general lesson.** `IF NOT (a = b)` is not safe in PL/pgSQL when either side can be
NULL. `admin_spend_by_user` and `audit_chain_verify` have the same shape and were safe,
because `is_superadmin()` is an `EXISTS` and so always a real true or false. The audit's
section 6 lists this shape so a new one gets read.

### SA-2026-11-06-02: one's own id, and someone else's credential

The same guard let a signed-in user through on `auth.uid() = _user_id`, and the query
then ignored `_user_id` whenever `_scope_type` was set. So a user passing their own id
with `_scope_type = 'embed_key'` and another tenant's key id got that key's spend.
Measured: user B read `0.45` from a key whose traces were not theirs. Passing a NULL
`_user_id` made the guard NULL, as above, and worked too. Now only the service role and
superadmins can ask about a scope, which the browser never did.

### SA-2026-11-06-03: publishing into every tenant's samples

Rows with `is_sample = true` are readable by everyone. The INSERT policies on most of
these tables refuse the flag, but no UPDATE policy looked at it, and `kb_sources` and the
`kb_graph_*` tables did not check it on INSERT either.

Measured: user A set `is_sample = true` on their own table. User B could see 0 of A's
rows before and 1 after. The same worked on `knowledge_bases`, and with an INSERT on
`kb_sources`. This is what makes it High: agents retrieve from knowledge bases and write
SQL from dataset contents, so text one tenant publishes this way reaches another
tenant's agents as if the platform had supplied it, which makes it a stored prompt
injection across tenants.

Fixed with a trigger on all ten tables with the flag, because a policy cannot see the
old value. It refuses a client setting the flag, and leaves every other edit alone.
Service-role and migration writes are unaffected, and nothing in the client ever set it.

### SA-2026-11-06-04: writing into the shared samples

The browser seeded the samples by calling `upsert_sample_dataset` and
`insert_sample_rows`, with content it supplied. Both checked only that a user was signed
in, so anyone could add any rows to a sample every tenant reads, or create a new one.
Measured: `upsert_sample_dataset('poison', ...)` returned a new sample's id.

Both functions are dropped. The server now seeds the samples, from the CSVs the build
ships with, and the browser sends only its token and whether to refill.

### SA-2026-11-06-05: skipping the contact form

`/api/contact` validates, rate-limits and checks a honeypot, then writes with the service
role. A policy also let `anon` insert directly, which skipped all of that, and could set
`status` and `admin_notes` as well. Measured: an anonymous insert with a forged
`admin_notes` succeeded. The policy and the grant are gone, and the form is unchanged.

### SA-2026-11-06-06: the avatars bucket

The bucket is public and had no size or type limit. The 5 MB limit was only in the page,
and the page accepted SVG, which can carry script. It now enforces 5 MB, and PNG, JPEG,
WebP or GIF, in the bucket itself and in the page.

### SA-2026-11-06-07: grants nothing needed

Supabase grants `anon` and `authenticated` everything by default, and row-level security
does the real work. It held: no policy let `anon` write once the contact policy went.
But a table that ever shipped without row-level security would have been writable by the
signed-out world. `TRUNCATE` ignores row-level security altogether, and both client roles
held it, though the database API does not expose it. These grants are revoked, also for
tables created later. Measured, of 169 tables: `anon` could write to 164, and both client
roles could truncate 168. Neither can now touch any.

## Has a running install been affected?

The audit's section 12 lists samples somebody owns. Every real sample has no owner, so
any row there was published by a user, and should be read before being removed:

```bash
docker exec -i supabase-db psql -U postgres -d postgres < docs/security/scripts/schema-audit.sql
```

Rows added to an existing sample leave no such mark. If you run several tenants and want
to check, compare each sample's row count with its CSV in `src/assets/sample-data/`.

## Left as they are

- **The seven functions `anon` can still call.** Five are helpers that row-level
  policies call (`is_superadmin`, `has_resource_access`,
  `has_unrestricted_resource_access`, `is_swarm_approver` and `can_access_workspace`).
  Policies are evaluated as `anon` too, so revoking these would turn an empty result into
  an error on signed-out reads. They answer yes or no about a user id the caller already
  has. The other two are `increment_blog_view`, a public counter, and `bi_touch_view`,
  which does nothing without a user.
- **`notebook_runtime_settings` is readable by every signed-in user.** It holds limits,
  which the pages need. It also holds `spark_connect_url`, so a token must never be put
  in that URL.
- **`prune_agent_memory_items`** has a NULL-affected guard that is harmless: a NULL
  `_user_id` skips the check, and the delete that follows then matches nothing.
- **`vector` lives in `public`**, which is how Supabase installs it.
- **`chat-docs` and `datasets` have no bucket limits.** Both are private, and the server
  enforces upload limits.
