# Security assessment — 2026-10-25

First full assessment under the process in [../README.md](../README.md). It
combines automated scanning (dependencies, images, secrets) with a line-by-line
review of the authentication, authorization, Row-Level-Security, SSRF and
SQL-safety surface.

**Headline:** the dependency and image hygiene is good and the RLS _table_
coverage is complete (every table in `public` has RLS). The real exposure is a
cluster of **`SECURITY DEFINER` RPCs and RLS policies that key on a
caller-supplied id instead of `auth.uid()`**, and one **read path that runs
attacker-controlled SQL on the shared analytics engine**. These allow
cross-tenant reads and cross-tenant writes between signed-in accounts. None
require being an operator; several require only knowing a target resource's
UUID.

## How this was run

- **Dependencies:** `npm audit` (production and dev), with the lockfile and the
  Python service requirements also read by osv-scanner.
- **Images:** Grype against the five first-party images and the base/third-party
  images the compose stack runs.
- **Secrets:** gitleaks over the working tree and history.
- **Code / config / RLS:** manual review of every `src/routes/api/*` handler,
  the `createServerFn` server functions, all `supabase/migrations`, the SSRF
  guard and its callers, the read-only SQL guard, and the production server's
  response headers.

Scanner versions used are recorded in the run directory under `../reports/`
(git-ignored); re-run with `bash docs/security/scripts/scan.sh`.

Confidence is marked per finding: **confirmed** (traced through the code here),
or **likely** (consistent with the code but not executed). Severity follows
impact and reachability, not theory.

## Findings

### Critical

**VA-2026-10-25-01 — Delta-sharing row filters run as raw SQL on the shared
engine (cross-tenant read).** Confirmed (reproduced). **Fixed in R376.**
A lakehouse share's row filter is stored as a raw SQL fragment
(`src/utils/lakehouse/shares.functions.ts`), pasted unchanged into the served
query (`policies.server.ts` → `shares.server.ts`, a `COPY (…)`), and executed on
the one DuckDB engine that has every tenant's schema attached, with external
access left on. Tenant isolation is enforced only over the _recipient's_ own
SQL (`governSelect`), not over the filter the sharer wrote. A user can share
their own table with a filter such as `n IN (SELECT <col> FROM victim.table)`,
mint a delta-sharing token, and read another tenant's rows (and likely files /
env via error-based extraction). **Fix:** run the delta-sharing query on a
sandboxed engine (`enable_external_access=false`, no cross-schema attach) and/or
validate that a stored filter references only the shared table's own columns.

### High

**VA-2026-10-25-02 — Read-only SQL guard bypassed by a comment inside a string
literal.** Confirmed (reproduced in the Workbench). **Fixed in R374.**
`src/lib/sqlSafety.ts` `structureOnly()` strips `--`/`/* */` comments _before_
string literals, so `SELECT '--' ; DROP TABLE t` reduces to `SELECT '` — the
`;` and the second statement vanish from the inspected text while the database
still runs both. This is the shared guard for every local engine and every
warehouse driver (`assertReadOnlySql`), and a shared warehouse connection runs
as its owner. **Fix:** make the strip literal-aware in a single left-to-right
pass (the lakehouse's `stripComments` in `utils/lakehouse/sqlRefs.ts` already
does this correctly); add regression cases with comment markers inside literals.

**VA-2026-10-25-03 — `match_gateway_cache` reads any user's cached answers.**
Confirmed. **Fixed in R375.**
`public.match_gateway_cache(p_user_id, …)` (migration `20260870000000`) is
`SECURITY DEFINER`, filters on the **parameter** `p_user_id`, and is never
revoked from client roles — so any authenticated user can call it over PostgREST
with another user's id and read that user's cached gateway questions and
answers. **Fix:** `REVOKE EXECUTE … FROM anon, authenticated, public` (the app
calls it as the service role).

**VA-2026-10-25-04 — Forged ML-promotion approval takes over another user's
model.** Confirmed. **Fixed in R377.**
`mlApplyApprovedPromotion` (`ml.functions.ts` → `ml/promote.server.ts`) trusts
an `approvals` row whose RLS is `FOR ALL USING auth.uid()=user_id`; nothing
checks the caller is in `model.promotion_approvers` or that the version belongs
to the model. An attacker inserts a self-owned "approved" row naming a victim
model and their own artifact, then applies it — the victim's model serves the
attacker's version. **Fix:** server-side, verify the approval belongs to the
run/model and the caller is a designated approver before applying.

**VA-2026-10-25-05 — ML API keys can be planted on another user's model.**
Confirmed. **Fixed in R375.**
`ml_api_keys` RLS (`20260858000000`) checks only `user_id`;
`authenticateMlApiKey` loads `key.model_id` without comparing owners. A user
inserts a key row naming a victim model, then calls predict/train, and
`register … promote:true` can swap production. **Fix:** RLS `WITH CHECK` that the
named `model_id` is owned by `auth.uid()` (mirror the `swarm_api_keys` fix in
`20260813000000`); defence-in-depth owner check in `authenticateMlApiKey`.

**VA-2026-10-25-06 — MCP server keys can be planted on another user's app.**
Confirmed. **Fixed in R375.**
`mcp_app_keys` RLS (`20260756000000`) checks only `user_id`; the proxy
(`api/mcp.s.$slug.ts`) checks only `key.app_id === app.id`, and `is_internal` is
caller-set, so a planted key reaches private servers and is invisible to the
owner's list/revoke. **Fix:** same shape as VA-05 — `WITH CHECK` tying the key's
`app_id` to an app owned by `auth.uid()`; do not let the client set
`is_internal`.

**VA-2026-10-25-07 — Forged approval resumes another user's parked swarm run.**
Confirmed. **Fixed in R377.**
`swarmResume.functions.ts` reads the caller's own approval row then loads
`approval.swarm_run_id` with `supabaseAdmin`, with no check that the approval
belongs to that run or its approvers — so a victim's run resumes, as the victim,
skipping the designated approvers. **Fix:** verify the approval's run and
approver membership server-side.

**VA-2026-10-25-08 — Grantees can bypass row filters and column masks.**
Confirmed (two paths) + likely (views). **Fixed in R378** (the two materialize paths).
`matviews.server.ts` checks the schema then runs `CREATE OR REPLACE TABLE
mine.x AS <sql>`, and `importDatasetToLakehouse` (`lakehouse.functions.ts`)
copies every row with the service role without `restrictSharedDataset` — both
materialise a shared dataset's full, unmasked rows into the grantee's own
schema. Related (likely): a view created while access was held keeps returning
rows after the grant is revoked, because governance walks only the statement's
own tree. **Fix:** apply the same row-filter/column-mask restriction on the
materialise/import paths; expand views during governance or drop dependent views
on revoke.

**VA-2026-10-25-09 — Unrevoked `SECURITY DEFINER` ML/sample RPCs (cross-tenant
write).** Confirmed. **Fixed in R375.**
A superseding migration re-creates a function under a new signature, which
reverts EXECUTE to PUBLIC. Affected, none revoked, all keyed on an id argument
with no `auth.uid()` check: `ml_job_record_shard` (4-arg, `20260914000000`),
`ml_job_advance_phase` (6- and 7-arg, `20260912/20260915`),
`increment_ml_deployment_use`, `record_ml_shadow_result`,
`record_ml_canary_result`, `seed_bi_sample_dashboards`, `seed_bi_sample_extras`.
A read-only ML share recipient gains a write/corrupt path to the owner's
training jobs and canary/rollback counters. **Fix:** `REVOKE EXECUTE … FROM
public, anon, authenticated` on each new signature (service-role only).

### Medium

**VA-2026-10-25-10 — Public embed chat knowledge-base scoping.** Confirmed.
**Fixed in R379.**
The reviewer flagged `api/embed.chat.ts` retrieving citations with the service
role and no owner scope. The current code _does_ pass `userId: keyRow.user_id`
(the key owner) and `principal: { anonymous: true }`, which drops `private` /
`source_acl` connector documents. The remaining question was narrower: whether
`retrieveCitationsServer` enforces that the configured `kbIds` are **owned by**
that user, so an owner cannot wire a victim KB id they merely learned (e.g. an
ex-grantee). Verified: on this path it did not. The owner-scope filter in
`tools/kb.server.ts` runs only when `scopeUserId` is set, and the embed path set
`userId` but not `scopeUserId`, so a wired foreign KB id was searched (the
anonymous principal drops per-document ACL content, not a whole KB). **Fix:**
pass `scopeUserId: keyRow.user_id` on the embed retrieval call, so the filter
bounds `kbIds` to the owner's own KBs, public samples, and IAM-granted ones.

**VA-2026-10-25-11 — A user a secret is shared with can extract its
plaintext.** Confirmed. **Fixed in R380.**
`api/a2a.ts`, `testLlmGateway` and `testNotificationChannel`
(`integrations.functions.ts`) resolve `{{secret:NAME}}` — including
IAM-shared secrets — into an `Authorization` header sent to a caller-chosen
endpoint. A grantee points the endpoint at their own server and receives the
secret. **Fix:** in caller-supplies-endpoint paths, resolve only secrets the
caller **owns**, not ones merely shared with them. `resolveSecretRefs` /
`resolveIntegrationConfig` gained an `ownedOnly` option that skips the IAM-grant
fallback; the a2a invoke and the two live tests (which take a caller-supplied
URL) pass it. The real chat/swarm/warehouse send paths keep the default, so
legitimate _use_ of a shared secret is unchanged. (A sibling read — a shared
secret resolved into an MCP-app sandbox env the grantee controls, in
`notebook.runtime.source.ts` — is **VA-2026-10-25-28, fixed in R382**; it is
endpoint-less and was outside this finding's "caller-supplies-endpoint" scope.)

**VA-2026-10-25-12 — Email endpoints enable branded phishing.** Confirmed.
**Fixed in R381.**
`/api/email/send` lets any signed-in user send any template to any address with
caller-controlled `templateData` (links built from `siteUrl`); `/api/contact`
(unauthenticated) emails attacker-controlled text to any address, skips the
suppression list, and rate-limits on a spoofable `x-forwarded-for`. **Fix:**
`/api/email/send` now refuses a template with no fixed recipient unless the
recipient is the caller's own account email (the only real caller is the welcome
email to the user who just signed up; a fixed-recipient template such as an admin
notice is still allowed). `/api/contact` now gates the confirmation email — the
one addressed to a visitor-supplied address — on the suppression list and a
per-recipient cap (keyed by the recipient, not the spoofable IP header), so a
spoofed `x-forwarded-for` cannot flood a chosen victim; the admin notification
and the stored message are unchanged.

**VA-2026-10-25-13 — Users can erase or zero their own LLM-cost records.**
Confirmed. **`execution_traces` fixed in R383 (migration applied); the `swarm_runs` half is split out
as VA-2026-10-25-31.**
`execution_traces` and `swarm_runs` RLS is `FOR ALL`, so a user can `DELETE`
their rows or `UPDATE cost_usd = 0` over PostgREST, defeating the spend a
superadmin's budget cap is measured on. **Fix:** split the policy — `SELECT`
for the owner, but `INSERT/UPDATE/DELETE` service-role only (the app writes
traces as the service role). **Scope note:** the budget cap is measured only on
`execution_traces` (`budgetSpend.server.ts`), and all seven of its write sites
are server-side — so the table was split now and its three sites that still used
the caller's client (the chat route, the python-notebook route, the dev
`seedTraces`) were moved to the service role. `swarm_runs` does **not** feed the
budget cap, and its writes come from the browser bundle (the in-page swarm tracer
and the cancel path), which cannot hold the service-role key — locking it needs a
server-function refactor, so it is tracked separately as VA-2026-10-25-31.

**VA-2026-10-25-14 — Several outbound fetches skip or under-check the SSRF
guard.** Confirmed (several) + likely (rest).
Raw `fetch` of a user/model-supplied URL, not through `safeFetch`:
`providers/ollama.functions.ts`, `providerModels.functions.ts`,
`icebergCatalogs.functions.ts`, provider `base_url`
(`providers/credentials.server.ts`, `adapters/openai-compat.server.ts`). Others
check only the literal hostname with no DNS resolution and default
`redirect:"follow"`: `connectorFetch.server.ts`, `git/exporter.server.ts`,
`catalog/objectStoreRead.server.ts`, `catalog/orcIsolated.server.ts`, warehouse
drivers, and `catalog/objectStore.server.ts` (signed S3 GET, unchecked). A name
resolving to a blocked range, or a redirect from an allowed host, reaches the
always-blocked metadata range — contradicting the guard's stated "nothing can
enable it". **Fix:** route these through `safeFetch` (resolves the name,
re-checks every hop); apply `assertEndpointAllowed` to the S3 GET.

**VA-2026-10-25-15 — Shared Parquet mirror directory may allow cross-tenant
read.** Likely (needs the glob-inside-allowed-dir check).
Every tenant's Parquet mirror lives in one directory
(`utils/data/parquet.server.ts`), the sandbox allows that whole directory
(`duckdb.server.ts`), and mirrors carry no row filter or column mask. If
globbing inside an allowed directory is permitted with
`enable_external_access=false`, user SQL can enumerate and read other tenants'
mirrors; if not, it needs the exact `tableId.stamp` filename. **Fix (either
way):** a per-query allow-list limited to the files the query's own tables
loaded. _To verify:_ run `glob`/`read_parquet('<dir>/*.parquet')` against the
real sandboxed engine.

**VA-2026-10-25-33 — WITHDRAWN: not a finding.** Filed during R386 as "the
lakehouse page shows the catalog database password", from the attach error the
page displayed after a Docker restart. The evidence was misread: the script
that read the page masked `password=…` itself before printing, so what the
page actually showed was never seen. The boot path the error came from
(`lakehouseEngine`) already re-throws it through `redactLakehouseSecrets`,
which masks the libpq and URL forms and the configured values themselves, and
`lakehouseErrorRedaction.test.ts` pins that exact message — fixed in an
earlier round, found from the UI the same way. Kept here so the number is not
reused.

**VA-2026-10-25-16 — All profiles' PII readable by any authenticated user.**
Confirmed; partly intentional.
`public.profiles` SELECT is `USING (true)` for `authenticated`
(`20260504100311`), exposing every user's name, avatar, role, org and bio, and
giving the `user_id` enumeration that makes VA-03 reachable. Deliberately a
directory, but instance-wide. **Fix / accept:** scope to shared
workspaces/groups if a global directory is not required; otherwise record as
accepted with the reason.

**VA-2026-10-25-28 — A shared secret resolves into an MCP-app sandbox env its
grantee controls (endpoint-less read).** Confirmed (reproduced against the live
build). **Fixed in R382.**
The sibling VA-11 flagged as tracked separately. `mcpAppBundle`
(`src/routes/api/notebook.runtime.source.ts`) resolved each `KEY={{secret:NAME}}`
in an MCP app's `secret_refs` with the DEFAULT (shared-allowed) resolution and
returned the values as the sandbox's `env`. The app's OWNER writes its
`source_code`, so a grantee authors `print(os.environ)`, references a secret
merely shared with them by IAM grant, starts the runtime and reads the plaintext
— no caller-chosen endpoint needed, so it fell outside VA-11's scope. The file's
own comment ("a sandbox cannot reach a secret its owner could not") was true for
owned secrets and false for shared ones: the owner may _use_ a shared secret but
is not meant to _see_ it, and in a sandbox they can. **Fix:** resolve
`secret_refs` with `{ ownedOnly: true }` (the option R380 added), so only secrets
the owner owns resolve into the sandbox; a shared binding is dropped and the tool
that needed it reports a missing variable. "Use without seeing" is not
enforceable in a sandbox the caller controls, so no legitimate use is lost.
Sibling sandbox-env injections were audited: swarm Function/component nodes and
notebook kernels receive no resolved secret, and the ML / Spark-query env
resolves no user `{{secret:NAME}}`. Two are the same class and left open: ETL's
`python`-node env resolves `secret_refs` and node secrets shared-allowed into a
sandbox the pipeline owner controls (**VA-2026-10-25-29**); and two
caller-chooses-endpoint paths R380 did not reach — the swarm HTTP node
(`swarmNodes.server.ts`) and the catalog connectivity test on source create
(`catalog.functions.ts`) — forward a shared secret to a caller-supplied URL
(**VA-2026-10-25-30**).

### Low

- **VA-2026-10-25-17** — Budget cap enforced only on `/api/chat`, embeds,
  `/api/swarm/run` and the gateway; missing on `/api/python-chat` (falls back to
  the operator key), `/api/bi`, `/api/{etl,lakehouse,skills}/generate`,
  `kb/build-graph`. Confirmed. **Fix:** apply `getBudgetDecision` on these.
- **VA-2026-10-25-18** — Workflow trigger rate limit inverted
  (`workflows.run.ts`: valid triggers get 429 until the bucket drains, then are
  unlimited). Confirmed. **Fix:** invert the condition.
- **VA-2026-10-25-19** — `api/public/hooks/refresh-model-registry.ts` accepts
  POST with no auth and no throttle (outbound fetch + mass upsert/delete).
  Confirmed. **Fix:** require the internal/cron secret, or superadmin.
- **VA-2026-10-25-20** — `notebook.runtime.reap.ts` compares the cron bearer
  with `===`, not `timingSafeEqual`. Confirmed; low impact. **Fix:** constant-time
  compare.
- **VA-2026-10-25-21** — SSRF guard gaps in `ssrfGuard.server.ts`: only the
  `fe80:` prefix of `fe80::/10` is caught; a URL whose DNS lookup fails is
  allowed; DNS rebinding between check and connect is acknowledged but open.
  Confirmed. **Fix:** cover the full link-local range; fail closed on lookup
  error; pin the resolved address for the connection where feasible.
- **VA-2026-10-25-22** — The production server (`server.mjs`) sets no
  Content-Security-Policy, `X-Content-Type-Options`, `X-Frame-Options`/
  `frame-ancestors`, `Referrer-Policy` or HSTS. Confirmed. **Fix:** add a
  security-header middleware (CSP scoped to allow the embed routes' framing).
- **VA-2026-10-25-32** — `embed_keys`' policy checks only
  `auth.uid() = user_id`, not that the key's `resource_id` (agent, swarm or BI
  dashboard) is that user's, so a client can insert a key naming someone else's
  resource. Not reachable today: every loader re-checks the resource's owner
  against the key's `user_id` before serving. Found in the R385 review of the
  API keys hub. **Fix (defence in depth):** an ownership check in the policy's
  `WITH CHECK`, as R375 did for ML and MCP keys; needs a migration push.
- **VA-2026-10-25-34** — Spend a cap cannot see or stop. `/api/etl/generate`,
  `/api/lakehouse/generate`, `/api/skills/generate` and `/api/kb/build-graph`
  record no execution trace, so their cost never reaches month-to-date spend;
  and the embeddings made when a knowledge base ingests (`kb/ingest-github`,
  `kb/ingest-url`, template provisioning, source sync) are recorded but never
  ask the budget first. Found in R390: on the live instance a skills draft
  generated before the fix left month-to-date spend unchanged. **Fix:** record
  each of those calls, and ask the budget before embedding (an over-cap
  ingest keeps its documents and skips the embeddings, as when no provider is
  connected).
- **Other low (reviewer-reported, to confirm individually):** Teams `app_id` /
  Slack `workspace_id` squatting; IAM group enumeration to any user; account
  probing via `sheetsShareSet`; `listApproverDirectory` returns every email;
  `forgetVectors` can delete shared/sample KB vectors; `featureViewDelete`
  clears the online store before the owner check; promotion gate skipped on the
  experiment/API/schedule paths; a SaaS source's grantee can pick its streams.

## Image scan

**Grype (image CVEs):** attempted against all five first-party images and the
base/third-party images. In this local Windows / Docker-Desktop environment
grype's vulnerability-DB download stalled (reproduced against a 20 MB archive),
so no per-image CVE list was produced here. The scanner invocation is correct
and runs on a Linux CI runner, where grype reads the daemon's images directly
and the DB downloads without stalling; the script now also caches the DB in a
named volume. **This is the one scope item not completed locally** — it should
be run in CI and its output folded into this report. Posture note: the base
images (`node:22-slim`, `python:3.12-slim`, `apache/spark:4.2.0-python3`,
`postgres:16`, …) are current majors rebuilt from upstream, so OS-layer
remediation is a `docker compose build` refresh, not a code change; the Python
service dependencies are additionally watched by `npm audit`/Dependabot and
osv-scanner (see below).

**hadolint (Dockerfile hardening):** ran cleanly on all five Dockerfiles. The
findings are style/hardening, not vulnerabilities — chiefly `DL3008` (pin apt
package versions) and `DL3066` (non-numeric UID may not resolve on the host).
Folded into the container-hardening items (VA-24). No `latest`-tag or
add-with-remote-URL findings in the first-party Dockerfiles.

## Cross-ecosystem scan (osv-scanner)

osv-scanner read every lockfile, which surfaces two areas `npm audit` cannot:

- **VA-2026-10-25-26 — Python service dependencies.** The doc renderer and the
  notebook runtime pin versions with known CVEs, chiefly **`pillow 12.3.0`**
  (many high/critical image-parsing CVEs, fixed in 13.0.0) and **`cairosvg
2.9.0`** (fixed in 2.9.1), plus others across
  `docgen-service/requirements.txt` and `docker/notebook-runtime/requirements.txt`.
  **Fix:** bump the pinned versions and rebuild those images (validated by a
  render smoke). Open — a dedicated round (needs an image rebuild).
- **VA-2026-10-25-27 — Stale `bun.lock`.** osv flags **178** advisories in
  `bun.lock`, versus **1** in `package-lock.json` (the accepted Azure one). The
  app installs with `npm ci` (the Dockerfile), so `bun.lock` is a second,
  unmaintained lockfile pinning long-superseded versions — a trap for anyone who
  runs `bun install`. **Fix:** regenerate it from the current `package.json`, or
  remove it if the bun install path is not supported. Open.
